PRACTICAL EXPERIENCE / CORE HANDBOOK

项目级 AI 规范：AGENT.md / CLAUDE.md 最佳实践

在 Vibe Coding（氛围/感觉编码）时代，我们往往会遇到一个反直觉的现象：**工具越来越聪明，开发体验却可能越来越乱。** 

很多开发者会抱怨 AI Agent 经常“不听话”、“自作聪明写出了一堆冗余代码”，或者“每次新建会话都要把项目规范重新复制一遍”。

这背后的根本原因，在于我们没有为 Agent 提供一个**“核心大脑”与“项目宪法”**。在实际工程中，`AGENT.md` 与 `CLAUDE.md` 正是扮演这一角色的关键配置文件。它们是 AI Agent 长期生效的基线，帮助团队将 AI 编码能力转化为稳定、高质量、可交付的工程产出。

---

## 1. 为什么 AGENT.md / CLAUDE.md 至关重要？

我们可以把 AI Agent 看作是一个**“每次上班都会失忆的超级程序员”**。即使它拥有极强的编码推理能力，但每次开启新的 Session，它对你的项目都是一无所知的。

如果不进行约束，AI Agent 在面对任务时通常会有以下致命痛点：

* **上班失忆症**：会话一旦拉长，或者新建会话，AI 就会忘掉你之前口头交代的所有规范，开始随性发挥。
* **Token 黑洞与效率低下**：为了让 AI 理解项目，它可能会漫无目的地读取几十个文件，扫描整个目录，单次交互耗费数十万 Token。更糟糕的是，由于缺乏明确的构建和测试指令，AI 遇到报错时只能无限自我修复（Agent Loop），烧费大量时间与成本。
* **隐性技术偏差**：AI 默认会采用其训练数据中最主流的通用方案。如果你的项目有自研的组件库（例如长江电力项目中的 `Ds*` 库）、特定的脚手架或特定的 API 契约，AI 根本无从得知，只会一遍遍重复造轮子，写出与项目格格不入的代码。
* **无视“业务守恒原则”**：在进行代码重构或迁移时，AI 很容易因为理解偏差，凭空删减原有页面上的查询字段、权限按钮或接口契约，导致功能降级。

因此，`AGENT.md`（或等效的 `CLAUDE.md`、`.cursorrules`）就成了**上下文压缩技术**和**项目宪法**的载体。它把稳定的项目知识压缩在几 KB 的 Markdown 文件中，在 Agent 初始化时自动感知，从而让 AI 拥有了“长期记忆”。

## 2. 应该包含哪些核心内容？

一个合格的 `AGENT.md` / `CLAUDE.md` 绝不是一堆废话，而是只包含**模型无法从已有源码中推断出来的习惯、命令与红线**。它应该包含以下五个核心板块：

### A. 项目基础信息与技术栈归一 (Project Info)
明确指出项目所使用的语言、核心框架、数据库及 UI 组件库的版本。最重要的是**归一化技术选型**，防止 AI 引入不相关的依赖。例如：“本项目统一使用 Vue 3 + Ant Design Vue，严禁无故混用 Element Plus”。

### B. 常用环境命令 (Commands & Environment)
列出具体的构建、运行、测试和 Lint 命令。Agent 具有执行 Shell 命令的能力，写明 these 命令后，Agent 在修改完代码后能够**自我闭环验证**。如果代码通不过 Lint 或测试，它会自行修复后再交付，极大降低了人工介入频率。

### C. 架构约束与公共组件基线 (Architecture & Base Components)
告诉 AI 你的目录结构规范（如业务逻辑必须封装于 `src/services/`）以及 API 返回的统一数据契约。特别要指出**强制绑定的标准组件库**，严禁 AI 编写内联 style 或硬编码非 Token 的颜色与圆角。

### D. 8 大避坑红线与禁令 (DO NOTs)
记录项目绝对不能触碰的底线。比如：“严禁修改数据库迁移主键”、“严禁硬编码敏感 API Key，必须使用环境变量”、“修改后严禁将未通过单测的代码直接提交”。

### E. 业务守恒原则 (Business Preservation)
硬性要求 Agent 在做任何迁移与重构时，必须 100% 完整保留原有业务的查询条件、权限按钮、页签过滤和数据契约。

## 3. 标准的 MD 目录结构

以下是一个通用的、可直接复制的项目级 `AGENT.md` / `CLAUDE.md` 标准结构模板：

```markdown
# 项目核心指引 & 规范手册 (CLAUDE.md / AGENTS.md)

## 项目基础信息
- **技术栈**: React 18 (Next.js App Router) + TypeScript + Tailwind CSS + Prisma
- **状态管理**: Zustand
- **基础组件库**: Radix UI + shadcn/ui (位于 @/components/ui)

## 常用命令 (Commands)
- **启动开发服务器**: `npm run dev`
- **构建项目**: `npm run build`
- **运行单元测试**: `npm test`
- **代码格式化与检查**: `npm run lint`
- **数据库同步**: `npx prisma db push`

## 架构约束 (Architecture Rules)
- **逻辑分层**: 业务数据处理与第三方服务对接必须封装在 `src/services/` 下，页面组件仅负责数据渲染与交互。
- **数据返回**: 所有 API 统一返回格式为 `{ success: boolean, data: T, code: number, message: string }`。
- **公共组件绑定**: 页面上的按钮、输入框、下拉框必须优先从 `@/components/ui/` 导入，禁止自行编写基础 CSS 样式。

## 编码风格 (Code Style)
- **TypeScript**: 严格启用 strict 模式，严禁显式使用 `any`，必须为所有 API 入参和出参定义 Interface/Type。
- **命名规范**: 文件名与组件统一使用 PascalCase (如 `UserCard.tsx`)，普通函数与变量使用 camelCase。
- **异常处理**: 所有异步请求必须包含 `try-catch` 块，并调用全局 `toast.error` 统一向用户展示。

## 避坑红线 (DO NOTs)
1. **严禁修改** `prisma/schema.prisma` 中的历史数据模型，新增字段必须通过 Migration 或经导师确认。
2. **绝对禁止**将密码、Token 或 API Key 硬编码在代码中，必须配置在 `.env.local` 且不可提交。
3. **严禁**在组件内部编写超过 20 行的内联 CSS 样式。
4. **禁止**在执行修改时随意删除已有的接口参数，必须保持向下兼容。

## 业务守恒原则
- 在对旧页面进行重构或样式迁移时，必须确保以下内容 100% 对应，严禁漏写：
  - 所有的查询字段、重置按钮以及页签的默认过滤条件。
  - 组件绑定的权限控制标识 (如 `hasPermission('admin')`)。
```

## 4. 真实工程实战拆解：长江电力落地方案

在“长江电力新一代生产经营管理系统”这一超大型项目实战中，团队只有 4 名开发人员，却需要构建 **600+ 个页面**及极其繁琐的业务流程。

为了让 12 个异构协作团队在没有口头对齐的情况下，依然能写出完全一致的代码，团队制定了统一的 `AGENTS.md` 基线。

在长江电力的实战中，`AGENTS.md` 沉淀了以下高级工程法则：

### 规则 1：Skill 路由与任务映射
在大型工程中，如果让一个通用 coding 助手直接生成复杂页面，效果往往很差。长江电力将不同的任务强行路由给专属的“Agent Skills”（类似于特定的小助手工具），例如：“新增 Vue 页面必须调用 `frontend-page-builder` Skill”，让专用的模型与指令干专业的事。

### 规则 2：公共组件的“组件状态表”强绑定
为了杜绝开发人员和 AI 随意使用开源的第三方组件或自己手写内联 CSS，`AGENTS.md` 确立了组件的 **Fact Order (源码事实优先级)**。
当 AI 尝试寻找一个组件时，必须遵循以下优先级来引用：
> 组件状态表 > `index.ts` 导出 > Vue 源码 > Design Tokens > 业务页面 > 文档。

AI 会被强制从 `@/components` 导入 stable 状态的组件（如 `DsPage`，`DsFormGrid`，`DsDataTable`）。最终在 `AGENTS.md` 的强约束下，系统 1,156 个业务视图中有 1,021 个深度绑定了 `Ds*` 规范库，覆盖率高达 88.3%。

## 5. 如何使用与日常演进？

### A. 命名与等效关系
在不同的 Agent 生态中，有些工具倾向于读取 `.cursorrules`，有些工具如 Claude Code 默认感知 `CLAUDE.md`，有些智能体平台感知 `AGENT.md`。
这三者在核心解析权重与写法上**完全等效**。在实际项目中，你可以将它们配置为**符号链接 (Symlink)**：
```bash
ln -s AGENTS.md CLAUDE.md
ln -s AGENTS.md .cursorrules
```
这样，不管团队成员使用什么 IDE (Cursor) 还是命令行 CLI (Claude Code)，都可以共享同一份项目规范手册。

### B. 动态演进的“Living Doc”机制
`AGENT.md` 绝对不是写完就一劳永逸的静态文档，而是一个**与项目共同成长的 Living Doc**。

Vibe Coding 的核心心法之一就是**“持续改进闭环”**：
1. **AI 犯错**：在一次任务中，AI 写出了不符合预期的冗余代码，或者导致了编译报错。
2. **记录原因**：人工排查出 root cause（例如某组件升级了，参数名已改变，但 AI 还在用老参数名）。
3. **增加 Rule**：不要只在聊天框里教训它，而是把这条红线**立刻写进 `AGENT.md`**。
4. **自动避免**：下一次 AI 重新拉取上下文时，就会自动读取这一最新规则，以后自动避免同样的错误。

通过这种“AI 犯错 → 记录原因 → 增加 Rule → 以后自动避免”的闭环，你不仅是在完成当下的任务，更是在**把 AI 犯错的成本沉淀为项目长期的工程化资产**。这才是专业 Vibe Coding 研发体系的最核心杠杆。
